## 이 글에서 할 일

DB 설계는 앱의 뼈대입니다. 테이블 사이의 관계를 알면 기능이 어떻게 움직이는지 보입니다. Ledger의 테이블 12개를 묶음별로 정리합니다.

## 관계도

```text
app_user ─┬─< category ──────────────┐
          ├─< payment_method ───────┐│
          │                         ││
          ├─< ledger_entry >────────┘┘   (거래: 카테고리 필수, 결제수단 선택)
          │      │  └──> asset (적금 이체 연결, 선택)
          │      └──> bank_account (통장, 선택)
          │
          ├─< recurring_item ──< recurring_run ──> ledger_entry
          │   (고정 항목)          (월별 처리 기록)
          │
          ├─< asset
          ├─< bank_account ──< account_transfer (통장 간 이체)
          └─< recurring_transfer ──< recurring_transfer_run ──> account_transfer

holiday (전 사용자 공용)

──<  : 하나가 여러 개를 가짐 (1:N)
──>  : 다른 테이블을 가리킴 (FK)
```

## 테이블 묶음

### 사용자와 설정

| 테이블 | 역할 |
|---|---|
| `app_user` | 계정. 아이디, BCrypt 비밀번호 해시, 주기 시작일(`pay_day`), 주말 보정 여부, 시작 잔액 |

사용자 설정을 별도 테이블로 나누지 않고 `app_user`의 컬럼으로 두었습니다. 사용자당 설정이 한 줄뿐이라 나눌 이유가 없습니다.

### 분류

| 테이블 | 역할 |
|---|---|
| `category` | 수입, 지출 카테고리. 그룹 이름(`group_name`)으로 묶어 소계 |
| `payment_method` | 결제수단 (체크카드, 계좌이체 등) |

둘 다 **사용자마다 따로** 가집니다. 가입할 때 기본 카테고리와 결제수단을 넣어 줍니다. 거래가 쓰고 있는 항목은 지우지 않고 `active = false`로 숨깁니다.

### 거래

| 테이블 | 역할 |
|---|---|
| `ledger_entry` | 거래 한 건. 날짜, 수입/지출, 카테고리, 내용, 금액, 결제수단, 메모, 통장, 연결된 적금 자산 |

가계부의 중심 테이블입니다. 대부분의 조회가 "이 사용자의 이 기간 거래"라서 `(user_id, entry_date)` 인덱스를 둡니다.

```sql
CREATE INDEX idx_ledger_entry_user_date ON ledger_entry (user_id, entry_date);
```

### 고정 항목

| 테이블 | 역할 |
|---|---|
| `recurring_item` | 매달 결제되는 항목. 결제일, 보정 방식, 할부 정보, 달러 금액 |
| `recurring_run` | 항목의 **월별 처리 기록**. `(recurring_id, period_ym)`이 기본 키 |

`recurring_run`은 이 설계의 핵심입니다. "2026-10월분을 처리했다"를 한 줄로 남기고, 같은 달을 두 번 기록하지 못하게 기본 키로 막습니다. 자세한 동작은 [고정 항목 자동 기록](/posts/ledger-domain-recurring)에서 다룹니다.

### 자산과 통장

| 테이블 | 역할 |
|---|---|
| `asset` | 통장, 적금, 주식 잔액표. 주식은 종목과 수량, 시세 |
| `bank_account` | 통장. 기준 잔액과 기준일, 기본 통장 여부 |
| `account_transfer` | 내 통장 사이의 이체 |
| `recurring_transfer`, `recurring_transfer_run` | 월급날 정기 이체와 그 월별 처리 기록 (고정 항목과 같은 구조) |

### 공용

| 테이블 | 역할 |
|---|---|
| `holiday` | 공휴일. 모든 사용자가 함께 씀. 날짜가 기본 키 |

## 설계 원칙 1. 잔액은 저장하지 않고 계산한다

가계부라면 "이번 달 잔액" 컬럼이 있을 것 같지만, Ledger에는 잔액 컬럼이 없습니다. **거래를 더해서 매번 계산합니다.**

| 잔액을 저장하면 | 계산하면 (Ledger) |
|---|---|
| 지난달 거래를 고치면 그 뒤 모든 달의 잔액을 다시 고쳐야 함 | 고친 거래가 다음 계산에 바로 반영 |
| 저장된 잔액과 실제 거래가 어긋날 수 있음 | 어긋날 수 없음 (진실은 거래 하나) |
| 조회가 빠름 | 매번 SUM. 개인 가계부 규모에서는 충분히 빠름 |

통장 잔액도 같습니다. 은행 앱에서 본 잔액을 **기준 잔액**으로 한 번 적어 두면, 그 뒤의 거래와 이체를 더해 현재 잔액을 계산합니다.

```sql
-- 통장(체크카드 연결)별 잔액과 통장 간 이체. 잔액은 저장하지 않고 기준 잔액 + 기준일 이후 기록으로 매번 계산한다.
```

시트에서 "달이 바뀌면 남은 돈을 손으로 옮겨 적던" 불편을 없앤 것이 바로 이 원칙입니다([이월 계산](/posts/ledger-domain-opening-balance)).

## 설계 원칙 2. 금액은 원 단위 정수(BIGINT)

```sql
amount BIGINT NOT NULL CHECK (amount > 0),   -- 원 단위 양수. 수입/지출은 type 으로 구분
```

- **실수(FLOAT, DOUBLE)를 쓰지 않습니다.** 실수는 `0.1 + 0.2`가 `0.30000000000000004`가 되는 것처럼 오차가 생깁니다. 원화는 소수점이 없으므로 정수가 정확합니다.
- **`BIGINT`**: `INT`는 약 21억까지라, 큰 자산이나 누적 합계에서 넘칠 수 있습니다.
- **금액은 항상 양수, 방향은 `type`으로**: 지출을 음수로 저장하면 "지출 합계"를 구할 때마다 부호를 뒤집어야 하고, 실수로 음수 수입을 넣을 수도 있습니다. `CHECK (amount > 0)`으로 막습니다.
- 달러 금액과 환율처럼 소수가 필요한 곳은 `NUMERIC(12, 2)`, `NUMERIC(20, 10)` 같은 **정확한 소수 타입**을 씁니다.

## 설계 원칙 3. 모든 사용자 데이터에 user_id

```sql
-- 모든 사용자 데이터 테이블은 user_id 로 격리한다. 조회 쿼리는 항상 AND user_id = #{userId} 를 건다.
```

`holiday`를 빼고 모든 테이블에 `user_id`가 있습니다. [사용자 조건](/posts/ledger-mybatis-user-scope)의 바탕입니다.

## 정리

- 테이블 12개: 사용자, 분류(카테고리와 결제수단), 거래, 고정 항목과 처리 기록, 자산과 통장과 이체, 공휴일.
- 잔액은 저장하지 않고 거래로 계산해, 과거를 고쳐도 어긋나지 않습니다.
- 금액은 원 단위 양수 `BIGINT`, 방향은 `type`, 소수가 필요한 곳은 `NUMERIC`입니다.
- 모든 사용자 데이터에 `user_id`가 있습니다.
